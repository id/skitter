# ADR-001: Task.id Deduplication and Multi-Turn Conversations

**Date:** 2026-03-23
**Status:** Accepted

## Context

Skitter needed a mechanism for multi-turn conversations with generated app agents. A user chatting with an app sends multiple messages over time, and each message triggers a new coordinator session (DAG execution). The question: how should conversation continuity work?

The coordinator maps the incoming A2A `Task.id` to a DB session ID: each inbound request creates exactly one session, and `Task.id` serves as the primary key for tracking that session's lifecycle (pending, in-flight, completed, failed).

### Spec Constraints

Two specifications govern the behavior:

**A2A v1.0 (HTTP-based)** defines two orthogonal identifiers for conversational continuity:

- `task_id`: unique per task. Terminal states (completed, failed, canceled, rejected) are final; the task cannot accept new messages. The only case where you send another message to the same `task_id` is when the task is in an interrupted state (`INPUT_REQUIRED`, `AUTH_REQUIRED`).
- `context_id`: groups related tasks into a conversation. A new message with the same `context_id` but a new `task_id` starts a new task in the same conversation thread.

**A2A-over-MQTT v0.1** mandates deduplication: "Responders MUST use `Task.id` to deduplicate retried requests. If a responder already has state for a given `Task.id`, it MUST return the existing task state rather than creating a duplicate." It does not define a multi-turn primitive; each `message/send` with a new `Task.id` is a new task.

## Options Considered

### Option A: Relax dedup for completed sessions

Remove the DB check for completed sessions. If the session is done and cleaned from memory, let a new request with the same Task.id create a fresh session.

- Pro: simple, enables "chat" by reusing the same ID.
- Con: violates both specs (Task.id must be unique per task in A2A; dedup is mandatory in A2A-over-MQTT). Loses retry protection for completed sessions.

### Option B: Each turn gets a fresh Task.id; introduce context_id for conversation threading

The client generates a new `task_id` (UUIDv4) per message but includes a stable `context_id` (also UUIDv4) to group related tasks into a conversation. The `context_id` field is defined in the A2A v1.0 base spec (`Message.context_id`) but is not part of the A2A-over-MQTT v0.1 transport binding; skitter adopts it as an application-level extension, carried inside the JSON-RPC `message` payload alongside `taskId`. Agents are not required to interpret `context_id`; it is opaque to them. The coordinator uses it to query prior session results when building context for new turns.

This preserves the 1:1 mapping between `Task.id` and DB session, so individual session lifecycle tracking stays intact; multiple tasks (turns) are grouped by `context_id` instead.

- Pro: compliant with both A2A v1.0 and A2A-over-MQTT. Clean separation between retry handling and conversation continuity. Sets up the "per-chat conversation history" roadmap item.
- Con: more work; requires `context_id` plumbing through the stack and a future conversation history feature.

### Option C: Allow reuse only for completed sessions

Check if the existing session is completed; if so, allow the new request to proceed (creating a new session row).

- Pro: simple, works without `context_id`.
- Con: violates A2A task lifecycle semantics (completed tasks are terminal). Conflates retry and new-turn semantics.

## Decision

**Option B.** Each chat turn is a new Task with a new Task.id; conversation continuity uses `context_id`.

## Remaining Work

- **Conversation history via context_id**: when the coordinator sees a new `task_id` with an existing `context_id`, pull prior session results from the DB and inject as context for the new session's agents.
- **`INPUT_REQUIRED` support**: for tasks needing follow-up input (same `task_id`, interrupted state), keep the session alive in a paused state. This is Extended Conformance territory.
